# 成年困局真人试玩主持手册

> 目标：用同一个构建版本完成三名目标玩家的规则试玩，观察理解与选择，不教玩家怎样赢。

## 样本与分配

| 记录编号 | 起手身份 | 建议玩家背景 |
| --- | --- | --- |
| P1-01 | 名校毕业生 | 不限卡牌经验 |
| P1-02 | 职校技术员 | 不限卡牌经验 |
| P1-03 | 灵活就业者 | 不限卡牌经验 |

- 玩家应当没有参与本原型的设计。
- 尽量包含至少一名从未玩过卡组构筑游戏的玩家。
- 不记录姓名和联系方式；只使用记录编号。
- 开始前说明观察者会记录游戏行为和部分原话，征得玩家同意。

## 启动试玩构建

P1-A首轮批次必须先切到冻结标签，再按标签内的锁文件安装依赖并启动；不能先在开发分支安装依赖：

```powershell
git switch --detach playtest-v1.4.0-p1
npm ci
npm run playtest
```

第一条命令只把当前目录临时切到冻结构建；不要在这个状态下编辑源码。未来复测批次使用其批次清单指定的新标签，不能继续沿用P1-A，也不能直接用当时的HEAD代替冻结标签。

这条命令会先生成生产构建，再显示两个地址：

- `Local`：在主持人的电脑上打开。
- `Network`：同一可信 Wi-Fi 内的手机或电脑打开；若防火墙询问，只允许“专用网络”。不要在公共 Wi-Fi 上开放。

若终端没有显示 `Network` 地址，就让玩家使用主持人的电脑，不临时安装穿透或公网分享工具。三位玩家全部结束后按 `Ctrl+C`，确认终端回到命令提示符，再运行 `git switch feature/v2-adult-prototype` 返回包含校验工具的开发分支。

## 每位玩家的流程

1. 打开标题页，确认分配的身份入口可见。
2. 只告诉玩家：“请解决这场合同困局。页面上的信息都可以使用。”
3. 第一次出牌前，请玩家用自己的话解释目标、世界意图、倒计时、身份被动和牌会去哪里。
4. 玩家操作时不要解释克制、惯用手、三式、换手或童年余温；只追问“你现在在考虑什么？”
5. 逐轮记录玩家首先注意到的牌、最终选择、另一张候选牌、理由与误判。
6. 结案后按 `PLAYTEST_TEMPLATE.md` 的顺序访谈，不先问“好不好玩”。
7. 在结案页保存客观记录：
   - 本机 `localhost` 可以点“复制本局试玩记录”；
   - 通过局域网地址访问时，优先点“下载本局试玩记录”，避免浏览器拒绝非安全来源的剪贴板权限。
8. 第一份客观记录保存后，打开Markdown，从“构建版本”字段读取实际版本；建立名为 `playtest-版本号/` 的独立目录，并用实际值替换“版本号”。随后检查三份记录的“构建版本”完全一致，在记录空位填写匿名编号，把下载文件重命名为 `P1-01-原文件名.md` 这类格式，再与同编号观察笔记放进该目录。修复后复测必须升级版本并另建目录，不能覆盖或混入旧证据。
9. 点击“返回标题，换一个身份”，再交给下一位玩家。

## 三份客观记录校验

三位玩家全部结束并停止试玩服务后，在项目目录运行：

```powershell
git switch feature/v2-adult-prototype
npm ci
npm run validate:playtest -- "playtest-版本号"
```

第一条命令在前一步已经执行过时会安全地保持当前分支；第二条按开发分支自己的锁文件恢复制作工具依赖。把“版本号”替换为客观记录中的实际值。如果工具报告批次无效，先按提示修正编号或整理文件；若版本、身份或轮次事实确实不一致，不进入综合判断，也不修改客观事实来凑齐样本。观察笔记仍由执行制作人工检查，工具不会判断玩家理由或感受是否充分。

## 立即中止并上报

以下情况不继续凑样本：

- 页面白屏、无法继续或结案按钮消失。
- 记忆牌永久丢失、结算分数与预览不一致。
- 玩家遭遇明显不适并希望停止。
- 导出的身份或轮次与页面不一致；或记录缺少构建版本、三份记录的构建版本不一致。

记录复现步骤和客观文件，由执行制作先处理阻断问题；修复后升级构建版本，旧版本样本不与新版本混合。

## 阶段1有效样本

一份样本只有同时满足以下条件才计入：

- 玩家独立完成或明确选择停止，不由主持人代打。
- 主持人没有提前解释策略。
- 有玩家自己的规则解释和至少两轮选择理由。
- 有结案客观记录，或因阻断中止时有明确复现步骤。
- 记录包含构建版本和匿名编号。

三份样本齐备后，按 `PLAYTEST_SYNTHESIS.md` 的预注册门槛综合，并只选择一个最高影响问题。阻断、规则错误、身份伤害或使目标玩家无法继续的单次严重问题不需要重复出现；单人偏好和纯装饰意见不直接进入开发任务。若所有门槛已经通过，不强行制造改动。
