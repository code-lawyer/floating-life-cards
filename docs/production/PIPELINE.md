# 完整制作流程与阶段门槛

## 工作周期

项目不使用“想到什么就加什么”的推进方式。每个周期固定执行：

1. 选择当前最高风险或最高依赖任务。
2. 写清玩家目标、规则、非目标和验收标准。
3. 先做最小可验证实现。
4. 自动测试并进行真实界面验收。
5. 比较结果与设计目标。
6. 保留、修改或删除方案。
7. 更新文档、任务状态和下一周期。

## 阶段0：制作基础

目的：让之后的所有改动可追踪、可回退、可验证。

工作：

- 初始化Git仓库并记录v1稳定基线。
- 确认忽略构建产物、依赖和临时截图。
- 固定构建、测试与开发命令。
- 建立制作文档、系统地图、任务池和质量定义。
- 记录当前23项测试与生产构建结果。

退出条件：

- 任意改动都能看到差异并安全回退。
- 新参与者只读文档即可知道当前阶段和下一任务。
- 构建与测试在干净环境中可重复。

## 阶段1：玩法预制作

目的：验证成年牌局核心乐趣，不追求完整内容和最终美术。

工作：

- 使用10张固定记忆牌和3个身份被动。
- 制作1场四至五轮的成年困局。
- 实现回忆堆、每场一次童年余温和清楚的出牌预览。
- 比较单卡回合与有限双牌回应，默认先做单卡。
- 制作调试入口，快速重开同一困局。
- 进行内部规则测试与至少3名目标玩家试玩。

退出条件：

- 玩家不需要外部说明即可理解牌不会永久消失。
- 至少有两种有效打法，没有唯一显然最优牌。
- 玩家能解释记忆、身份和当前困局为何发生作用。
- 一场困局有继续玩的欲望，而不是只想跳过看文本。

三人规则试玩的具体人数阈值、身份安全否决、证据优先级与复测版本隔离见 `PLAYTEST_SYNTHESIS.md`。若当前构建直接达到门槛，不为了制造改动而调整玩法；若未达到，只修唯一最高影响问题。

若未通过：只改成年玩法，不扩童年内容。

## 阶段2：垂直切片

目的：用最少内容证明两个阶段真的连成一款游戏。

范围：

- 7–12岁六次选择，候选池至少12个事件。
- 一次普通、重点或技能倾向的路线选择。
- 一页童年总结和一次时间跳切。
- 三个成年起手身份。
- 一次组牌和阶段1的成年困局。
- 基础教程、移动端与存档。

退出条件：

- 小学选择能明显改变路线、身份候选或成年牌局。
- 玩家能追溯身份形成的至少三个原因。
- 从开局到成年困局没有解释断层。
- 完整切片没有阻断流程的错误。
- 试玩者愿意尝试第二局不同选择。

只有通过垂直切片，才估算和批准全部内容生产。

## 阶段3：系统生产

目的：让所有核心系统达到功能完整。

工作：

- 补齐4–17岁动态童年规则。
- 实现五个起手身份。
- 实现五场成年困局的规则框架。
- 完成成年事件、人生状态、结局和档案字段。
- 完成内容校验器、调试面板、批量模拟和存档新版本。
- 将大文件按内容与规则边界拆分。
- 将现有成人原型端到端测试扩展到完整故事、恢复与全部核心流程。

退出条件：

- 所有核心系统存在并能够从头走到结局。
- 内容可以通过数据文件添加，不需要改React规则。
- 测试覆盖主要状态转换和非法操作。
- 不再计划新增大型系统。

此时进入功能冻结；之后优先修正和填内容。

## 阶段4：内容生产

目的：把已验证系统填充为完整游戏。

工作批次：

1. 童年早期4–6岁。
2. 小学7–12岁与三条路线。
3. 青少年13–17岁和回响事件。
4. 五个身份的时间跳切。
5. 五场成年困局。
6. 成年选择事件、结局和专属回响。

每批内容都经过：

- 创意提案。
- 规则字段检查。
- 叙事初稿。
- 敏感表达审查。
- 实现与内容校验。
- 自动测试。
- 游戏内通读与修改。

退出条件：

- 目标内容量全部进入游戏。
- 没有死分支、坏ID、缺文案和无法触发的关键回响。
- 各身份都有独特处境，也都能抵达多种结局。

## 阶段5：Alpha

定义：功能与内容完整，但仍可能不平衡、不够顺滑。

工作：

- 全流程内部测试。
- 批量种子模拟。
- 修复阻断与严重规则错误。
- 调整资源曲线、身份分布和章节难度。
- 精简解释过多、重复或无回响的内容。
- 完成教程、键盘、移动端和打印档案。

退出条件：

- 无已知阻断错误。
- 普通玩家可以不用开发者帮助完成一局。
- 核心指标进入质量计划的目标区间。

## 阶段6：Beta

定义：玩法和内容原则上冻结，只接受修正、平衡和高价值可用性调整。

工作：

- 20–30名外部玩家完整试玩。
- 记录理解障碍、卡点、身份偏见和文本疲劳。
- 多设备、多浏览器与弱网络验证。
- 存档升级、恢复和重开检查。
- 建立正式部署、版本号、更新说明和隐私说明。

退出条件：

- 无阻断或高风险错误。
- 教程、完整通关和移动体验达到目标。
- 所有发布检查有明确负责人和证据。

## 阶段7：发布候选

工作：

- 只修发布阻断问题。
- 从干净环境安装、测试、构建和部署。
- 检查正式URL、缓存、错误页面和版本信息。
- 保存发布构建与已知问题。
- 准备反馈渠道和回滚方案。

退出条件：

- 同一构建通过全部自动测试和人工发布清单。
- 正式环境可完成从标题到结局。
- 能回退到上一个稳定版本。

## 阶段8：发布后

- 先修阻断、存档和数据丢失问题。
- 再修平衡与体验问题。
- 最后判断新身份、新事件、多周目档案柜和声音是否值得开发。
- 不根据少量强烈反馈立即改变核心设计，先汇总重复问题和实际数据。
